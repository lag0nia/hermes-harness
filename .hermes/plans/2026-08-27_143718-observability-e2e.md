# Hermes Observability E2E Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task. Every production-code task follows strict RED → GREEN → REFACTOR. Do not promote phases automatically.

**Goal:** Implement a privacy-preserving, durable E2E observability layer that reconstructs each user turn across Hermes and the Control Plane, diagnoses failures from cited evidence, and proves the initial shadow/read-only integration through reviewed traces on CLI/TUI, Desktop, and Telegram.

**Architecture:** Build a standalone `hermes-observability` plugin and a typed MCP bridge in `hermes-harness`, without modifying Hermes core. The plugin and harness use the same additive `observability-event-1.0.0` contract and write sanitized events directly to a central SQLite WAL database under `/opt/data/hermes-harness/var/`. Normal telemetry is queued and fail-open; critical audit records are written synchronously and fail-closed before any side effect.

**Tech Stack:** Python 3.13, Pydantic 2, SQLite WAL, HMAC-SHA256, MCP Python SDK 2.x, Hermes native plugins/hooks/CLI, pytest, pytest-asyncio, Hypothesis, Ruff, mypy, JSON Schema, Git/GitHub Actions.

## 1. Scope and non-negotiable invariants

1. `default` remains the only user-facing entry point.
2. Do not modify Hermes core under `/opt/hermes`.
3. Do not persist prompts, user messages, assistant answers, tool arguments/results, HTTP headers/bodies, cookies, credentials, tokens, card data, or authenticated browser state.
4. All payloads pass through one central sanitizer before validation and persistence.
5. External user/chat IDs are pseudonymized with HMAC-SHA256 using a local key generated once, stored with mode `0600`, and never exported.
6. Internal `session_id`, `turn_id`, `job_id`, `trace_id`, `span_id`, and `parent_span_id` remain available for correlation.
7. One root trace represents one user turn. Each routed intention, specialist, tool, LLM request, approval, Kanban task, delivery attempt, or Control Plane operation is a child span/event.
8. Normal telemetry: asynchronous, bounded queue, fail-open.
9. Critical audit: synchronous transaction, never dropped, fail-closed before a side effect if persistence cannot be proven.
10. Queue saturation may discard the oldest normal metrics only; it records a sanitized loss counter when capacity returns.
11. Each query returns at most 200 events and uses cursor pagination. Models receive bounded summaries and citable `event_id` values, not raw traces.
12. SQLite logical limit: 512 MiB. Purge expired data first, shed normal telemetry near the limit, and never sacrifice a pending critical write. Degrade normal telemetry when free disk falls below 500 MiB; block side effects when critical audit cannot be persisted.
13. Retention is 30 days for ordinary traces. A whole trace manually marked as an incident, with a mandatory reason, is retained for 180 days. No one-year anonymous metrics store is created. Event criticality controls write durability; incident status controls extended retention.
14. Browser screenshots remain ephemeral and are deleted on success, failure, and cancellation.
15. No proactive incident alerts in this version. On a failed job, `default` includes a short diagnosis, evidence, next step, and short trace ID in its normal answer.
16. Successful traces retain verification evidence but are summarized to the user only on an explicit audit/debug request.
17. Diagnostics are written in English. The deterministic classifier runs first. A bounded LLM explanation cites `event_id` values:
    - primary slot: `observe_diagnose_luna`, `openai-codex`, `gpt-5.6-luna`, effort `high`;
    - technical fallback only: `observe_diagnose_terra`, `openai-codex`, `gpt-5.6-terra`, effort `high`;
    - if both fail technically, return the deterministic diagnosis;
    - never change provider or use parallel model fallback.
18. Commercial actions remain blocked: purchase/order submission, cart mutation, checkout, payment, tip, final booking/reservation, or anything capable of creating a charge.
19. The initial live phase permits read-only, inspect, search, and plan only. Non-commercial mutations may exist in policy design with exact confirmation, but they are not exercised or enabled during initial E2E acceptance.
20. No automatic promotion. Moving from shadow to live read-only requires at least 24 hours of shadow evidence, trace review, green gates, rollback readiness, and explicit user approval.
21. Purge is available only from a human CLI, never as an agent/plugin tool. It requires preview, count, digest, exact confirmation valid for 30 minutes, and irreversible deletion.
22. Exports are local, sanitized, manual, mode `0600`, stored in `var/exports/`, accompanied by a manifest/digest, and deleted after seven days. Agent-triggered export is exposed only to `default` and `engineer` and still requires an explicit user audit/export request.
23. Normal database access is append-only. Retention/purge uses a separate maintenance API unavailable through agent tool schemas.

## 6. Main risks and mitigations

1. **SQLite multi-process contention:** short transactions, WAL, busy timeout, idempotency, stress tests, bounded normal queue, synchronous critical receipt.
2. **Sanitizer bypass through new hook fields:** closed event unions, unknown-field rejection, one sanitizer entry point, property tests, serialized canary scans.
3. **Broken cross-surface correlation:** explicit `(profile, session_id, turn_id)` root mapping, child span IDs, synthetic and live common-case tests.
4. **Critical audit falsely treated as telemetry:** separate APIs/types, typed exception, side-effect guard tests, code review search for swallowed `AuditUnavailable`.
5. **Retention versus append-only semantics:** normal writer has no mutation API; maintenance operations are isolated, audited, CLI-only, and confirmation-bound.
6. **Untrusted plugin breadth:** minimum capabilities, no core patch, no credentials, pinned SHA, doctor/security review, per-profile enablement.
7. **Diagnostic hallucination:** deterministic classifier is authoritative; LLM receives bounded evidence and may cite only supplied IDs.
8. **Accidental live mutation during E2E:** closed phase-policy matrix, fail-closed unknown intents, no commercial schemas, live acceptance limited to read-only.
9. **Partial eight-profile rollout:** install disabled everywhere first, verify exact SHA/doctor everywhere, then coordinated enablement with rollback.
10. **Overclaiming readiness:** phase labels and per-route/per-surface acceptance matrix are mandatory.
